# Decisions и четыре профильные очереди

Текущая настройка10/20 и предварительный отсев: [evaluation-performance.md](evaluation-performance.md).
Ниже также сохранены исходные результаты режима10.

Новый режим включается полем `routing` в конфиге анализатора. Legacy-запуски без
этого поля сохраняют последовательный LangGraph first-PASS. Коллектор не меняется.

Текущая политика оценки и выдачи — [applications.md](applications.md): без вопросов
владельцу, с конкретной подборкой для отклика. Прежний strict v2 ниже сохранён для истории.

## Что происходит с карточкой

1. Код берёт полную сохранённую версию вакансии. Поисковые семейства остаются
   происхождением обнаружения; они не являются готовой классификацией роли.
2. `decisions.py` передаёт полное название и описание в **native Decisions API**:
   `POST /v1/decisions`, model `gpt-6-luna`, один вопрос `choice=primary`.
   Это не Responses/Chat Completions. Резюме и предыдущие оценки не передаются.
3. Сохраняется распределение пяти классов: Product, автоматизация, ассистент, BA,
   other. Код проверяет полноту, конечность и сумму вероятностей.
4. Если лидирует other, карточка получает ROUTING_REVIEW. Она не удаляется и не
   считается отказом кандидату. Иначе первый профиль выбран; второй добавляется,
   когда разность вероятностей двух ведущих **профильных** классов `p1-p2 <= margin`.
   Максимум два; точные равенства разрешаются Product → automation → assistant → BA.
5. Четыре очереди имеют по одному воркеру. Одновременно до4модельныхвызовов,
   каждый с **одним полным резюме и до10или20полных вакансий своего профиля**. Последний
   батч может быть меньше10. При превышении ограничения входа батч делится;
   одиночная слишком большая карточка остаётся с технической ошибкой, без обрезки.
6. Оценки карточек независимы. Два назначенных профиля могут работать одновременно;
   оба завершаются даже после раннего PASS. Карточка не проходит всех четырёх по кругу.

Пример: Product0.48, automation0.45, BA0.04, assistant0.02, other0.01;
при margin0.05 карточка попадает в Product и automation. Разность0.03, обе оценки
сохраняются. Это иллюстрация правила, не измеренный пример из калибровки100.

Новый координатор — обычный Python/ThreadPoolExecutor; LangGraph не управляет
этими четырьмя очередями. Оценщики вызываются через native Codex CLI и существующий
ChatGPT login, `gpt-6-luna`/`max`, без инструментов, общей памяти и API-ключа в prompt.

## Результат

| Состояние назначенных оценок | Итог карточки |
|---|---|
| Хотя бы один PASS | ACCEPTED; обе назначенные оценки всё равно сохраняются |
| PASS нет, назначенная оценка отсутствует/ошибочна | PENDING |
| Все назначенные завершены, есть BORDERLINE | NEEDS_CLARIFICATION |
| Все назначенные дали REJECT | REJECTED_BY_SELECTED |
| Лидирует other | ROUTING_REVIEW |

NOT_ROUTED означает, что профиль не назначен; это не REJECT. REJECTED_BY_SELECTED
означает отказ только одного/двух выбранных профилей. Legacy REJECTED означал
четыре валидных отказа; смешивать эти исходы нельзя. Если первый PASS сохранён,
а вторая назначенная оценка ещё не завершена, карточка уже ACCEPTED, но весь run
остаётся partial: `incomplete_selected_evaluations` показывает остаток.

## Запуск и продолжение

Шаблон: [analysis.routed.example.json](../configs/analysis.routed.example.json).
Пути считаются относительно JSON. Нужно указать четыре приватных CV, calibration
JSON с `policy_hash` и `margin`, и существующий workspace native Decisions helper.
`prepare` сверяет hash текущей таксономии с калибровкой и фиксирует её hash/порог.

На данном сервере подключение — существующий `openbot-openai-api`; он хранит ключ
в штатном зашифрованном хранилище. Анализатор не извлекает и не копирует ключ.
Request/receipt файлы допускаются только внутри существующего OpenBot data root;
новый приватный подкаталог workspace подготавливается отдельно, без смены auth.
Это текущая серверная интеграция, не переносимый SDK для произвольного компьютера.

```sh
# Сначала фиксация входов, без сетевых вызовов
uv run --no-sync python -m career_scout.analysis prepare --config private/analysis-routed.json --limit 100 --max-calls 16
uv run --no-sync python -m career_scout.analysis run RUN_ID --db data/analysis-routed.sqlite3
uv run --no-sync python -m career_scout.analysis status RUN_ID --db data/analysis-routed.sqlite3
# Сохранённый остаток бюджета; готовые ответы не повторяются
uv run --no-sync python -m career_scout.analysis resume RUN_ID --db data/analysis-routed.sqlite3
# Явно разрешить дополнительные batch calls и поколение повторов
uv run --no-sync python -m career_scout.analysis resume RUN_ID --db data/analysis-routed.sqlite3 --retry-errors --additional-calls 4
uv run --no-sync python -m career_scout.analysis export RUN_ID --db data/analysis-routed.sqlite3 --output data/routed-results.json
```

Оба внешних пути выключены общим `external_calls_enabled=false` в примере;
`routing.max_requests=0` дополнительно запрещает категоризацию. `max_requests`
ограничивает резервирования маршрутизации, `max_calls` — **Codex-батчи**, а не
отдельные вакансии. Сотня карточек может создать до200назначенных оценок.
Неравные очереди нормальны: источники и профили не получают искусственных квот.

До обращения резервируется бюджет, состав батча и поколение. После сбоя вызов
может быть учтён без ответа; это консервативный расход, не доказанная цена.
Проверенные оценки сохраняются отдельно по карточкам; повторяются только отсутствующие
или ошибочные, с конечным `max_attempts_per_profile`. Успешные9из10 не повторяются.
Нативная квитанция Decisions переиспользуется; неизвестный исход или ошибка
сохранённого запроса останавливает маршрут без слепого платного повтора.
Увеличения routing-budget CLI пока нет: его задают до `prepare`; успешные решения
можно переиспользовать по body hash из того же workspace в новом run.

Один исполнитель на analysis DB под flock; главный поток единолично пишет SQLite.
У потоков модели нет DB-соединения. Новые таблицы добавляются без удаления старых
inputs/evaluations/attempts/checkpoints. Сборщик и его volume не изменяются.
Ctrl+C завершает только принадлежащие этому исполнителю worker process groups.
Батчевые usage учитываются один раз, не десять раз. Цена подписки неизвестна.

## Калибровка100

Протокол, данные и ограничение: [отчёт](decisions-routing100-20261112.md).
Основной класс совпал с предварительной разметкой98/100. Владелец подтвердил, что
уверенного одного профиля достаточно; искать все допустимые альтернативы не нужно.
Рабочий margin0.10 добавляет второго оценщика только при разнице≤10п.п.
Пороги0.00…0.55 на development равнозначны, поэтому точная граница не установлена;
исходный численный optimum0 сохранён отдельно. На100карточках рабочий порог
даёт те же56одиночныхмаршрутов и44review. Шаблон выключает внешние вызовы.

Повторяемый runner: `scripts/calibrate_routing.py DIRECTORY --workspace ABS_PATH`.
DIRECTORY содержит приватные sample.json, labels.json и frozen-manifest.json
(SHA256 обоих файлов и policy_hash). Ровно100полных снимков; каждому соответствует
primary_profile, expected_profiles, split=development/holdout. Эталон не входит в
API input. Порог выбирается только на60development по microF1 множества профилей;
при равенстве — primary coverage, меньше вызовов, меньший порог.40holdout оцениваются
один раз без подбора по ним. Повтор runner читает native receipts вместо новых вызовов.
