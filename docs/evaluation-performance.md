## Рабочий проход

`routing.batch_size` допускает10или20. `routing.max_batch_characters` — отдельный
предел транспорта: например400000для20полныхкарточек и JSON Schema. Он не меняет
резюме, факты, правила и ключи прежних оценок. При превышении предела батч делится,
текст не обрезается. Четыре воркера и одно резюме на батч сохраняются. Вызовы для
ошибочных элементов ограничены; успешные соседние результаты не повторяются.

## Decisions перед оценщиками

Режим включается явно через `routing.prescreen_policy_hash` и
`routing.fit_screen_policy_hash`, равные текущим POLICY_HASH соответствующих модулей.
Пример по умолчанию не включает сеть и не подставляет эти hashes автоматически.

Каждая карточка получает отдельный native Decisions request: исходный primary
choice и два независимых predicate про обязательный опыт строго больше3лет и
исключительно senior/lead-уровень. Отдельно работают до4APIзапросов одновременно.
Высокая вероятность≥0,995 и подтверждающий локальный фрагмент нужны для такого
жёсткого исключения. Желательный опыт, «от3лет», стаж компании, ассистент руководителя,
смешанный middle/senior и неизвестные значения остаются для оценки.

После выбора одного/двух профилей ещё один Decisions choice на каждый выбранный
профиль получает полное соответствующее резюме, инструкции, параметры и вакансию.
Три ответа: potential_match, clear_mismatch, uncertain. Только
`p(clear_mismatch) >= 0,995` исключает профиль; сомнительные передаются Codex.
Второй профиль проверяется независимо. Все выбранные явно исключены —
PRESCREENED_OUT; otherwise продолжается оценка оставшихся профилей. Other сохраняет
ROUTING_REVIEW. Решения Decisions никогда не становятся PASS для отклика.

Стабильный префикс полного резюме и правил помечен explicit cache breakpoint;
cache key≤64символов, вакансия находится после префикса. Версия CV/правил/параметров
меняет префикс и body hash. При одинаковых запросах потоки одного клиента используют
общую блокировку и сохранённую квитанцию. Повторных HTTP при неизвестном исходе нет.

До обработки карточки с fit-screen резервируется верхний бюджет3APIrequests:
маршрут плюс максимум два профиля. Это консервативное резервирование, не число
оплаченных запросов: other требует одного, часть квитанций переиспользуется.
При native_max_attempts=3 учитываются до трёх HTTP-попыток на операцию: всего до9накарточку и предел3600дляпорции400. Бюджет Codex считается отдельно.
Ошибка останавливает новые обращения; уже начавшиеся до4вызовов завершаются,
их успешные результаты сохраняет основной поток SQLite. Ошибка не означает отказ.

## Временные ошибки API

`routing.native_max_attempts` по умолчанию1, допустимо до3. Подтверждённые HTTP500/502/503/504
и429с rate_limit_error/slow_down повторяются ограниченно с увеличением паузы.
Квитанции исходного запроса сохраняются, новые попытки получают отдельные файлы;
успешная повторная квитанция затем переиспользуется. При доступном retry_after_seconds
пауза не короче указанной. Billing/quota,400/401/403, timeout и неизвестный исход не повторяются.
Это соответствует [рекомендациям API](https://developers.openai.com/api/docs/guides/error-codes).

На полном проходе первый503сохранил258маршрутов и остановил следующую передачу.
Тот же payload успешно выполнен во второй отдельно сохранённой попытке; первый
receipt не изменён. Продолжение сохранило CV, правила, snapshot и selection_key.
Изменены только операционные retry/budget: старая и новая конфигурации, причина и
отпечатки записаны в приватный operational-amendment-503.json.
