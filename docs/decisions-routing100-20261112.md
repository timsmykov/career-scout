## Подбор и контроль

Правило: назначить ведущий профиль; второй добавить при `p1-p2 <= margin`.
Если лидирует other, сохранить ROUTING_REVIEW. Сетка0…1 с шагом0.01;
оптимизируется microF1 множества ожидаемых профилей **только на60development**.
При равенстве выбираются primary coverage, меньше назначений, меньший порог.
Метрики40holdout получены после выбора; порог по ним не менялся. F1 полного множества
профилей оставлен как диагностика первоначального эксперимента; после уточнения
владельца полнота всех альтернатив не является критерием приёмки маршрута.

| Показатель | Development60 | Holdout40 |
|---|---:|---:|
| Совпадение основного класса | 58/60 | 40/40 |
| F1 множества профилей | 78.57% | 83.64% |
| TP / FP / FN назначенных профилей | 33 / 0 / 18 | 23 / 0 / 9 |
| Среднее число оценщиков на карточку, включая other | 0.55 | 0.575 |

Численный optimum по зафиксированному правилу — **margin0.00**. Все пороги0.00…0.55 дали одинаковый лучший
результат development, поэтому данные не выделили полезную границу внутри этого
интервала. Распределение всей сотни:56карточек → один оценщик;44 → ROUTING_REVIEW;
ни одной → два. В42случаях other соответствует эталону; ещё2ассистентские роли
R076/R092 ушли в review. Карточки не удалены и не получили кандидатский REJECT.

Два примера проблемы: R01 и R04 размечены как Product/автоматизация, но Decisions
выдал основному классу1.00, альтернативе0.00. Увеличение порога не создаёт
содержательную вторую вероятность: при равных нулях второй профиль выбирается
техническим порядком. При margin1.00 development F1 падает до70.09%, FP25.
Достаточной причиной для массового второго назначения это не является.

Уточнение владельца после просмотра результата: уверенный единственный профиль
считается достаточным; полное воспроизведение всех авторских альтернатив не является
требованием к маршрутизации. Поэтому0/25дополнительныхмаршрутов — диагностическое
свойство choice, а не блокер исполнения. Other по-прежнему отделён от отказа кандидату.

Рабочее правило установлено консервативно: **margin0.10**, второй профиль только при
разнице не более10процентных пунктов. На development это внутри равнозначного
оптимального интервала0.00…0.55; на всей сотне распределение остаётся тем же.
Точный ненулевой порог данные не выделили:0.10 — операционный выбор внутри плато,
не статистически доказанная граница. Исходная калибровка с optimum0.00 сохранена;
отдельная working policy содержит0.10 и причину выбора. Holdout не использован для
поиска нового оптимума. Смысловой подбор кандидату выполняют назначенные CV-оценщики.

## Исполнение батчей

Контракт и воспроизводимый запуск: [routing-batches.md](routing-batches.md).
Offline-тесты проверяют четыре одновременно работающих очереди по10, независимые
две оценки одной карточки, обработку ошибки одного элемента, budgets/cache/resume,
чужие ссылки на цитаты, сохранность прежних данных и отсутствие обрезки входа.
Реальный прогон:100зафиксированных карточек,14Product/12automation/12assistant/

отдельные батчи заняли4:46…8:31. Все40ответов валидны, технических ошибок0.

Затем сохранённый лимит4calls остановил обработку с16PENDING. Через штатный CLI
resume с дополнительными4calls выполнены батчи **4+2+2+8**, без повторения первых40.

наборе не получен; способность принять PASS проверена в прежних sanity-тестах и
offline-тестах нового режима. Распределение не выдаётся за оценку рыночной пригодности.
