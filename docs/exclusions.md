# Постоянный отсев вакансий

По решению владельца исключённая вакансия автоматически больше не анализируется.
Ключ реестра vacancy_exclusions — source + source_id. Реестр не зависит от резюме,
selection_key, campaign_id, модели и версии правил. Изменённое описание под прежним
ID, новый поиск, prepare --reprocess и resume не снимают исключение. Срока действия нет.

В реестр попадают:

- явный FILTERED_OUT кодового фильтра и подтверждённый архивный статус;
- окончательный other маршрутизатора (вне четырёх направлений);
- явное несоответствие после предварительного Decisions screening;
- REJECTED_BY_SELECTED, когда все назначенные оценки завершены отрицательно;
- подтверждённые dismissed/withdrawn/rejected из истории взаимодействия владельца.

Один REJECT при втором назначенном pending/PASS не исключает вакансию целиком.
Неизвестные значения, uncertain, незавершённые оценки, ошибка сети/модели и
исчерпанный бюджет не становятся бизнес-отказом. Легаси strict-v2 не переносится
автоматически в новый реестр. При первоначальном переносе истории учитывается
последний терминальный результат applications-1; более поздний ACCEPTED сохраняется.

## Проверки до передачи модели

1. prepare проверяет ID до создания WorkerInput, независимо от --reprocess.
2. run/resume снимает исключённые карточки с ранее подготовленных заданий.
3. Decisions routing и очередь Codex пропускают EXCLUDED; late response не может
   вернуть его в ACCEPTED. Технический report считает такой пропуск завершённым.
4. shortlist, поиск catalog и card ассистента скрывают исключённые карточки.
   Проверка catalog происходит до LIMIT/OFFSET, поэтому страницы и total корректны.
   card возвращает только excluded/source/id, без полного текста вакансии.

Реестр и его индекс находятся в отдельной базе анализатора. SQLite-триггеры
фиксируют терминальный отсев, включая записи процессов, запущенных до обновления
кода, и не допускают повторный INSERT задания для исключённого ID. Это позволяет
сохранить уже работающий проход. Сборщик и исходные вакансии не меняются.

Синхронизация кодовых фильтров читает SQLite коллектора mode=ro. Первый проход
берёт актуальные политики, последующие — новые события FILTERED_OUT по сохранённому
rowid, даже если до синхронизации появилась другая политика. Архивные карточки
также сохраняются в реестре. Состояния unknown/KEEP_UNKNOWN не исключаются.

Исходные входы, модельные оценки и причины сохраняются. При изменении статуса
старого задания на EXCLUDED прежние status/outcome копируются в exclusion_displacements.
По причине и origin_run/origin_key можно найти первоначальную оценку.

Автоматического восстановления нет. Существующая явная команда владельца reopened
может отменить только его собственный dismissed/withdrawn/rejected, с отдельным
аудитом exclusion_releases. Она не снимает исключения кодовых фильтров или моделей.
Смена резюме сама по себе ничего не восстанавливает.

Это учёт идентичности площадки. Другая публикация под новым ID не объявляется той
же вакансией по одному сходному названию; межплощадочное объединение остаётся
отдельной задачей.
