# Career Scout: от выдачи площадок к подборке под резюме

**Личный сервис · Python/SQLite · агентский CLI · 0.1.0 alpha · MIT**

## Задача

Один кандидат может искать несколько типов работы с разными резюме. Выдача
площадок пересекается, названия ролей неоднозначны, зарплата часто не указана,
а простое совпадение ключевых слов не показывает соответствие задач опыту.
Ручной обход быстро превращается в повторное чтение уже просмотренного.

Я спроектировал и собрал Career Scout: сбор полных карточек из четырёх источников,
локальное хранение, персональную оценку и конкретную подборку для откликов.
Разработка велась с помощью Codex; решения проверяются кодом, тестами и отдельными
живыми сценариями. Это alpha, без обещания стабильности или безошибочного отбора.

## Решения, определившие систему

**Надёжный сбор до модельного анализа.** API-страницы, окна публикации, source ID,
дочитывание, retry и checkpoints реализованы кодом. SQLite хранит исходники и
версии; после сбоя работа продолжается, а не начинается с первой страницы.
Следующий new скачивает полные описания новых ID. Это разделяет доступность
площадки и соответствие кандидата: ошибка API не становится отказом по вакансии.

**Кандидат описывается резюме, а не списком четырёх профессий.** Начальный
пользовательский сценарий превратился в версионированный контекст с произвольными
CV, целями и условиями. Настраивать его может агент через CLI с машинной схемой,
без ручного редактирования SQL и без общего сервера.

**Маршрутизация отдельно от смысловой оценки.** При нескольких резюме внешний
Decisions-коннектор помогает выбрать одно/два CV. Оценщики работают через подписку
Codex: одно полное резюме и до20независимых карточек в батче. Распределением,
бюджетами, кэшем и сохранением управляет код; LLM-координатор не требуется.

**Неопределённость не скрывается.** PASS, UNCERTAIN и REJECT имеют разные основания.
Проверяются цитаты, источник, идентичность карточки и охват пожеланий. Отсутствующий
навык не считается доказанным конфликтом; неизвестная зарплата не становится нулём.
Сами корректные цитаты не гарантируют правильной смысловой трактовки.

## Проверенный результат

| Свидетельство | Результат | Граница вывода |
|---|---|---|
| Предыдущий рабочий массив | Обработан фиксированный каталог9385карточек;985уникальных LLM-оценок | Старый сценарий владельца, не повторная приёмка generic-пути |
| Offline-приёмка0.1 | 484теста, сборка пакетов, Docker persistence | Выполнение и контракты, не рыночная точность |
| Полный установленный пакет | Сбор/resume/new → evaluation → shortlist/history | Явные эмуляторы HTTP/Codex |
| Живые источники | Поиск/detail всех4площадок;8HTTP-попыток | Ограниченная доступность в момент запуска |
| Живой персональный анализ | 4вымышленные карточки/2CV;3совпадения с исходной разметкой | Слишком мало для оценки общей точности |

Аудит нашёл и исправил два реальных сбоя: вложенную SQLite-транзакцию на границе
collection → evaluation и частичную запись истории при поздней коллизии event ID.
Рабочие прежние оценки сохранены. [Полная приёмка и ограничения](product-audit-0.1.md).

## Что уже полезно и что дальше

Сегодня сервис позволяет лично собирать каталог и получать подборку без повторного
ручного обхода. Профессию, запросы, число резюме и условия можно заменить через
контекст/план. Старые решения не выдаются за оценку по новым пожеланиям.

Для внешнего использования ещё важны самостоятельная поставка Decisions helper,
проверка установки с чужой учётной записью и широкая отложенная разметка качества.
Habr использует недокументированный frontend. Codex устанавливается отдельно.
Автоотсев Decisions по вероятности выключен по умолчанию; автооткликов и расписаний нет.
