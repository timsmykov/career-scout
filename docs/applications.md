# Отбор вакансий для отклика

По уточнению владельца12.11.2026 система использует уже собранные вакансии,
четыре полных резюме и заданные параметры. Вопросов владельцу нет. Пользовательская
выдача содержит только конкретные рекомендованные вакансии с подходящим резюме
и кратким основанием. Технические ошибки и исключённые карточки остаются в журнале.

## Решение по резюме

`evaluation_policy="applications-1"` и [applications.md](../prompts/applications.md)
в `common_prompt` включают новый режим. Он требует `routing`; четыре очереди,
Decisions, gap0.10, Codex subscription и батчи до10 сохраняются.

Вход WorkerInput по-прежнему v2; новая политика явно записана в filters и входит
в evaluation_key. Выход — ApplicationResult v3 с policy=applications-1.
[JSON Schema](../schemas/application-result.schema.json),
[вымышленный вход](../examples/worker-input-applications.synthetic.json),
[вымышленная рекомендация](../examples/application-pass.synthetic.json).

Решение PASS означает «имеет смысл откликнуться с этим резюме». Нужны подтверждение
основных задач и отсутствие существенного препятствия. REJECT означает «не включать
по текущим данным»; неизвестный навык не превращается в утверждение «не умеет».
`questions` всегда пустой, BORDERLINE в этой политике отсутствует.

В каждом основании сохраняются два разных признака:

- mandatory — насколько явно требование сформулировано работодателем;
- critical — без этого условия основная работа не соответствует подтверждённому
  опыту или есть существенное препятствие.

Неизвестная второстепенная деталь может остаться noncritical/unconfirmed при PASS.
Это не приписывает кандидату навык. Нельзя пропустить critical gap или доказанный
конфликт существенного обязательного условия. Advanced SQL, ключевая отраслевая специализация,
сложная инженерная разработка проверяются по глубине; базовая презентация или
незнакомый трекер не должны автоматически блокировать релевантную младшую роль.

Мягкое предпочтение по оформлению не равнозначно прямому запрету. Например,
«постоянная работа» в пожеланиях не доказывает отказ от стажировки с занятостью
до40часов, если владелец явно не ограничил оформление.

Факты берутся только из полного резюме и owner_attributes. География, зарплата и
формат не получают выдуманных ограничений. Резюме, общий и исследовательский профили,
авторизация и настройки OpenBot не меняются. Старые v2-оценки сохранены отдельно;
новая политика имеет другие ключи и не переименовывает прежний BORDERLINE в PASS.

## Следующие порции

`prepare --limit N` теперь выбирает **следующие N ранее не переданных входов**.
analysis_admissions хранит scope/route_key/run_id; scope фиксирует резюме, инструкции,
рубрики, параметры, модель, фильтры и правило маршрутизации. Изменение фактов или
правил создаёт новую версию анализа; дата campaign сама по себе не сбрасывает очередь.

Запуски prepare/run используют один flock на analysis DB. После сбоя ранее
подготовленный PENDING не теряется и не дублируется в следующем run; prepare возвращает
pending_previous_runs для продолжения. Если процесс оборвался после run_jobs, но до
admission, следующий prepare восстанавливает запись из сохранённого запуска.
`--reprocess` явно разрешает повторно подготовить прежние входы; валидный кэш остаётся.

```sh
uv run --no-sync python -m career_scout.analysis prepare --config private/analysis-applications.json --limit 100 --max-calls 20
uv run --no-sync python -m career_scout.analysis run RUN_ID --db data/applications.sqlite3
# Следующий prepare с теми же параметрами пропускает уже переданную сотню
uv run --no-sync python -m career_scout.analysis prepare --config private/analysis-applications.json --limit 100 --max-calls 20
# Для незавершённого прежнего запуска используется его resume
uv run --no-sync python -m career_scout.analysis resume PREVIOUS_RUN_ID --db data/applications.sqlite3
```

Подготовка ещё одной порции не запускает модель. Сборщик продолжает свой обход;
анализ читает только готовые full карточки через read-only соединение. Планировщика
и автоматического фонового обхода новых analysis runs нет: запуск остаётся ручным.

## Получение конкретной подборки

```sh
uv run --no-sync python -m career_scout.analysis shortlist --db data/applications.sqlite3 --limit 20
uv run --no-sync python -m career_scout.analysis shortlist --db data/applications.sqlite3 --profile product --limit 10
uv run --no-sync python -m career_scout.analysis shortlist --db data/applications.sqlite3 --run-id RUN_ID --output data/applications-shortlist.md
```

По умолчанию используется последняя версия параметров и резюме, результаты всех
её порций объединяются. Только ACCEPTED с валидным v3 PASS; старые strict-оценки,
вопросы, other, отказы и ошибки в подборку не входят. Более новая оценка того же
source/id не позволяет воскресить старый PASS. При фильтре профиля учитывается
PASS именно этого назначенного оценщика, включая второй профиль.

Выдача: ссылка, название, работодатель, профиль резюме и короткое основание.
Все входы `shortlist`, включая команду анализа и публикацию общего файла, учитывают
журнал отправленных откликов до применения LIMIT. `applied` убирает карточку из
вариантов для нового отклика, сохраняя оценку по резюме и доступ к самой карточке.
Явный `reopened` снимает ограничение истории; кодовые и модельные исключения
проверяются независимо. При синхронизации HH исходящие отклики различаются с входящими
приглашениями по данным самой площадки; время отправки сохраняется отдельно от
времени обнаружения записи. Повторное чтение того же факта не отправляет новый отклик.
Точные source/id не повторяются. Дата публикации проверяется относительно текущего
момента: максимум14дней; дата без времени допустима внутри окна, кроме неясного
нижнего граничного дня. Неизвестная/будущая дата не выдаётся как свежая. Межплощадочное
семантическое объединение одинаковых вакансий пока не реализовано.
Файл не перезаписывается и создаётся0600. Никаких откликов система не отправляет.

После исправления валидаторов `resume` может повторно проверить сохранённый wire
response без модельного вызова. Содержание не исправляется; источник и цитаты
проверяются заново, факт восстановления записывается в validation_recoveries,
прежние ошибки и usage сохраняются.

## Проверки

Offline проверяет продвижение2+2+1+0, сохранение прежних pending, восстановление
admission, новый scope при изменении параметров, две версии результатов, отдельные
источники цитат, отсутствие вопросов и выдачу только текущих рекомендаций.

[Контрольные9вакансий](../tests/fixtures/application-quality.json): четыре профильных
совпадения, желательный SQL, второстепенный офисный пробел, неподтверждённая центральная
Avro-специализация, явный конфликт advanced/basic SQL и подмена инструкций нерелевантной
работой. Ожидания зафиксированы до модели. Native Codex через4профильныхбатча дал9/9
совпадений, вопросов и технических ошибок0. Это авторские sanity-контроли, не рыночная
оценка точности. Общий quality runner также поддерживает новую политику через конфиг.

Полный проход снимка по площадкам: [full-array.md](full-array.md).

Постоянный отсев по ID, поверх версий admission: [exclusions.md](exclusions.md).
