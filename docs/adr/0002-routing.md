# ADR 0002: Decisions и четыре профильные очереди

Статус: новый режим утверждён владельцем12.11.2026; заменяет прежний маршрут
для новых запусков с routing. Рабочий gap для второго профиля≤0.10.

Владелец выбрал native Decisions API для категоризации и четыре параллельных
оценщика через свою подписку Codex. Одна карточка получает один или два профиля:
второй добавляется при p1-p2 <= margin. Решение основано на вероятностях одного
choice, а не на независимых predicate. Лидирующий other сохраняется для проверки.

Профильные очереди: product, automation, business_assistant, business_analyst;
этот порядок также разрешает точные равенства. У каждого профиля одновременно
один батч до10полных карточек и одно полное резюме. Для двух назначенных профилей
обе оценки сохраняются; PASS первого не отменяет вторую. PASS любого даёт ACCEPTED;
все назначенные REJECT дают REJECTED_BY_SELECTED, не общий отказ четырёх профилей.

Калибровка на60разработочных/40проверочных карточках дала основной класс98/100.
Владелец подтвердил: уверенного одного профиля достаточно, полный охват альтернатив
не требуется. Численный optimum0, плато0…0.55; рабочий порог0.10 выбран внутри
плато как консервативное правило. На сотне он не создаёт дополнительных назначений.
[Протокол](../decisions-routing100-20261112.md), [исполнение](../routing-batches.md).

Прежнее решение11–12.11: последовательный Product → automation → assistant → BA,
первый PASS завершает; общий REJECT требует четыре отказа. Оно сохранено только
в legacy analysis_graph.py и запускается, когда routing отсутствует в frozen config.
Индивидуальный кэш можно переиспользовать; route policy/агрегация различаются.
