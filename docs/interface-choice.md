# Интерфейс личного Career Scout и следующий этап

## Выбор

Первый CLI реализован: [команды, гарантии и ограничения](agent-cli.md).
Сравнение затрат агента на одинаковом полном сценарии CLI/MCP ещё предстоит выполнить.

Одна личная установка с собственными данными и подключениями. Основные операции
должны находиться в общей Python-библиотеке. CLI — первый прямой интерфейс для
локального агента с терминалом, скриптов и человека. MCP — тонкий адаптер тех же
операций для клиентов с нативными инструментами. Обязательный отдельный HTTP-сервис
или общий многопользовательский сервер в эту цель не входит.

MCP поддерживает локальный stdio и Streamable HTTP; наличие MCP само по себе не
означает публичный сетевой сервер. Схемы инструментов помогают обнаружению и
валидации аргументов. CLI требует столь же явного машинного контракта: JSON,
коды ошибок, help/schema и отсутствие обязательного интерактивного ввода.
Скорость и расход контекста сравниваются по реальному сценарию; превосходство
одного интерфейса по токенам не предполагается заранее.

Источники: [MCP transports](https://modelcontextprotocol.io/specification/latest/basic/transports),
[MCP tools](https://modelcontextprotocol.io/specification/latest/server/tools),
[CLI Guidelines](https://clig.dev/).

## Подготовительный блок: реализованные входы и оставшаяся семантика

Объединяет резюме, пожелания и план поиска. Агент передаёт полный текст1..Nрезюме,
свободные цели/предпочтения и известные формализуемые ограничения. Пожелание хранится
с источником и приоритетом; отсутствие неизвестного параметра не заполняется догадкой.
Агент формирует поисковые гипотезы, ядро проверяет план и переводит его для площадок.

CLI уже включает создание/чтение/изменение контекста, атомарные версии,
preview плана и выполнение с HTTP-лимитами. Профессионального enum в новых входах
нет; пожелания сохраняются свободным текстом. Поисковые гипотезы предоставляет
вызывающий агент. Полный контекст применяется новым context-1 потоком в Decisions и Codex;
[контракт и границы](context-evaluation.md). Прежний анализатор остаётся отдельным мостом.

## Decisions: прежний и персональный режимы

Текущий initial routing знает Product/automation/assistant/BA/other, а prescreen
включает фиксированные3года и senior-правило. Их нужно получать из контекста.
Основной смысл: потенциально релевантно человеку / явное несоответствие / неясно.
Если резюме одно, профессиональная классификация не нужна; при нескольких выбираются
resume_id. Существующий CV-fit screen с полным резюме можно переиспользовать.
Уверенность модели не заменяет проверку ложного отсева. В context-1 choices строятся по резюме; автоотсев выключен до проверки
качества. Прежние правила старых запусков сохраняются.

## LLM-оценка: тюнинг после определения контекста

Нужны контрольные случаи про основную работу, переносимость опыта, обязательное
и желательное, неполные навыки и смешанные функции. Сравниваются версии инструкций
на одинаковых входах с отдельной контрольной выборкой; меняется одно основание
за раз. Добавление обязательного ревьюера или обучение своего классификатора не
являются заранее выбранным решением.

## Подборка и explain

Подборка — конечный список вакансий для отклика с URL, условиями, подходящим резюме
и кратким основанием. explain — отдельное чтение свидетельств: на каком этапе и
по какому условию вакансия прошла/выбыла. Это не требование строить новый dashboard.
Существующая выдача и критерии не меняются этим планом.

## Личные установки

Каждый человек запускает свой экземпляр с собственным каталогом данных и доступами.
Общий сервер пользователей, tenant IDs, кабинеты и биллинг сейчас не нужны.
Раздельные резюме и отсутствие переноса чужих исключений сохраняются обычными
границами личной установки. История/импорт откликов и общая эксплуатационная
обвязка отложены по прямому уточнению владельца.

## Метрики качества: план

Измеряем по кандидатскому контексту, версии критериев, источнику и этапу:

| Показатель | Как определяется |
|---|---|
| Точность рекомендаций | Подходящие по контрольной разметке / все проверенные рекомендации |
| Потеря подходящих на этапе | Подходящие, ошибочно исключённые этапом / подходящие на входе этапа |
| Доля неясных | Неопределённые решения / все решения этапа |
| Ошибки исполнения | Технически не завершённые / назначенные операции |
| Полнота сбора | Сохранённые полные карточки / обнаруженные доступные ID в конечном плане |
| Время и потребление | p50/p95, запросы Decisions, батчи Codex и фактически известные tokens |
| Повторная работа | Повторные обработки уже готовых ключей; HTTP retries считать отдельно |

Если проверяется выборка ранних отказов, нужна разметка по разным слоям и учёт
долей выборки; нельзя выдавать долю ошибок проверенных отказов за recall всего
массива. Подходящее по одному CV не обязательно подходит по другому; разметка
привязана к конкретному контексту. Сначала доступный JSON/Markdown/CSV-отчёт,
затем удобное представление. Качество модели и техническая валидация разделяются.

Целевые численные пороги принимаются после baseline, а не объявляются достигнутыми.
Нужен проверяемый срез отсева, а не только прежние PASS. Обратная связь об отклике
сама по себе не является доказательством соответствия требованиям вакансии.

## Как проверить выбор интерфейса

После подготовки контекста сравнить одни операции через CLI и MCP: настройка,
изменение пожелания, запуск, чтение состояния, получение подборки. Считать число
действий/исправлений агента, ошибки аргументов, объём возвращаемого контекста,
задержку управления и сложность установки. Долгий анализ должен иметь run_id и
сохранённое состояние; жизненный цикл вычисления не должен зависеть от удержания
одного tool-вызова. Этот эксперимент и MCP-адаптер пока не реализованы.
