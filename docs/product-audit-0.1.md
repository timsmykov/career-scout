# Итоговая приёмка Career Scout 0.1.0

Исторический протокол до публичного обезличивания. Текущее состояние поставки —
[public-release.md](public-release.md); branch/connector детали ниже описывают ту проверку.

Статус: **полезная личная alpha-версия; стабильность 1.x не заявляется**.
Лицензия собственного кода — [MIT](../LICENSE). Аудит относится к текущей ветке
`feat/evaluation-workers`, а не автоматически к `main`. Его воспроизводимые
проверки входят в CI. Публикация релиза, слияние PR и изменение видимости GitHub
не выполнялись.

## Какую задачу уже решает продукт

Пользователь или его агент передаёт полные резюме, пожелания и поисковые запросы.
Career Scout собирает полные вакансии, хранит их локально, исключает повторную
передачу уже принятых карточек в рамках версии контекста и проверяет соответствие
резюме. На выходе — ссылки на вакансии для самостоятельных откликов, категория
резюме и основания оценки. Вопросов кандидату во время прохода нет.

Программа экономит ручное чтение выдачи и не теряет очередь при обычном
возобновлении. Следующий ручной сбор скачивает описания только новых ID.
Она не обещает найти все вакансии рынка, получить приглашение на интервью или
безошибочно понять каждое требование работодателя.

Для нового пользователя основной путь — **context → plan → collection →
evaluation → shortlist** через установленный CLI `career-scout`. Количество и
названия резюме произвольны; четыре прежних профессиональных профиля остаются
в отдельном совместимом режиме. [Первый запуск](quickstart.md).

## Состояние компонентов

Оценка относится к заявленному объёму 0.1, а не к процентам от неизвестного
будущего продукта.

| Компонент | Готово в 0.1 | Практическая граница |
|---|---|---|
| Настройка кандидата | Полные резюме, свободные пожелания и приоритеты, версии, явные fact_rules | Хорошие запросы составляет пользователь или вызывающий агент; CLI не придумывает стратегию поиска |
| Поиск | Настраиваемый план для HH, Habr, SuperJob, «Работы России», окно публикации | Доступны результаты настроенных запросов и разрешённой источником выдачи, а не весь рынок |
| Сбор | Полные карточки, нативные страницы, конечный HTTP-бюджет, checkpoints, initial/new/resume | API могут ограничить глубину или доступ; partial требует проверки отчёта и продолжения |
| Хранение | SQLite, идентичность source/source_id, исходники и версии, миграции с backup | Личная установка на Linux; общего сервера для нескольких пользователей нет |
| Нормализация | Зарплата, валюта/период/gross, опыт, формат работы; unknown/conflict видны отдельно | Неизвестные условия не угадываются; автоматического пересчёта налогов и валют нет |
| Условия до модели | Сопоставимые явно заданные ограничения проверяются кодом | Свободные пожелания передаются модели; отсутствующая зарплата не означает отказ |
| Decisions | Один/два динамических resume_id; отдельный бюджет и сохранённый маршрут | Для нескольких резюме нужен внешний native-коннектор; автоотсев по вероятности по умолчанию выключен |

## Что найдено и исправлено при приёмке

**Передача собранных карточек в generic-анализ не работала.**
`evaluation prepare --collection-run` открывал транзакцию SQLite, после чего
экспорт кампании повторно выполнял BEGIN. Удалено внешнее повторное открытие;
теперь реальный путь collection → evaluation проходит. Раньше тесты с готовым
JSON-каталогом не покрывали эту границу. Добавлены отдельная регрессия и
сценарий установленного пакета.

**Конфликт в конце импорта истории мог оставлять первые события пакета.**
Теперь весь пакет проверяется на коллизии operation_id до первой записи событий.
Регрессия подтверждает отсутствие частичного импорта при таком конфликте.
Это не обещание атомарности пакета при любых аппаратных сбоях: идентификаторы
событий по-прежнему позволяют сверить и продолжить прерванную запись.

Изменения: `src/career_scout/context_commands.py`,
`tests/test_context_engine.py`. Воспроизводимая проверка продукта:
`python3 scripts/check_product.py` после сборки Docker.

## Что проверяет новый полный сценарий

Сценарий запускает код **установленного пакета внутри образа**, без checkout
исходников, сети и реальных ключей. Используются настоящий HHClient с
контролируемым HTTP-транспортом и отдельный эмулятор executable Codex.

1. Создаёт одно произвольное резюме и обязательное пожелание удалённой работы.
2. Начинает сбор трёх карточек, останавливается по бюджету и продолжает тот же run.
3. Проверяет повтор request-id без HTTP и отсутствие дублей полных карточек.
4. Запускает новый сбор: выдача перечитывается, старые описания — нет.
5. Передаёт результат коллектора в analysis; выключенные вызовы блокируются.
6. Явно включает выполнение и получает PASS, REJECT, UNCERTAIN в одном батче.
7. Проверяет JSON-схему, цитаты, отдельную выдачу PASS/UNCERTAIN и explain.
8. Возобновляет готовый run без второго модельного вызова.
9. Импортирует факт отклика и проверяет исчезновение карточки из подборки.
10. Проверяет, что отсутствие разметки не выдаётся за измеренное качество.

Итого в сценарии: 5 эмулированных HTTP-попыток, 1 эмулированный Codex-батч,
0 реальных HTTP/модельных вызовов. Сценарий включён в обычный контейнерный CI.

## Существенные ограничения alpha

**Переносимость нескольких резюме ещё требует работы.** В текущем окружении
настроен `/usr/local/bin/openbot-openai-api`. Он не входит в пакет Career Scout;
на другом сервере потребуется собственный совместимый Decisions-коннектор.
Одно резюме при выключенном Decisions-отсеве маршрутизируется кодом и этого
коннектора не требует. Doctor пока проверяет полный набор подключений и может
вернуть ready=false без Decisions даже для такого допустимого сценария;
смотрите конкретные checks, а не только общий флаг.

**У Хабра нет подтверждённого публичного API поиска для этого адаптера.**
Используется проверенный frontend JSON/HTML; это более хрупкая интеграция.
Её нельзя называть четвёртым официальным API. Текущий живой probe успешен,
но будущая смена frontend может потребовать ремонта адаптера.

**Качество нового персонального отбора ещё не измерено достаточно широко.**
Живая контрольная проверка дала совпадение с разметкой в3из4 вымышленных случаев:
одна ожидаемая REJECT стала UNCERTAIN на противоречивом описании. Это оставшийся
разбор качества, а не доказательство 75% точности на рынке. Нужны отложенная
разметка нескольких кандидатов и отдельная оценка ложных отказов. Уверенная
вероятность Decisions не заменяет эту проверку.

**Преднамеренно отсутствуют:** публичный HTTP-сервис, UI/MCP-сервер, общий
multi-user backend, автоматическое расписание, автоматические отклики и
обновление всех ранее скачанных описаний. Следующий new добавляет новые ID;
содержимое и доступность прежней карточки могли измениться у работодателя.

Linux/Python3.12 — проверенная платформа. Работа на Windows/macOS не заявляется
этим аудитом. MIT покрывает собственный код; доступ к площадкам, право хранения
и использования данных, сторонние зависимости и подписки оформляются отдельно.

## Решение по первой версии

**Пользоваться уже можно** для личного сбора и подготовки подборки при доступных
площадках и настроенном исполнителе Codex. Один CV — самый простой переносимый
путь. У текущего владельца доступен и режим нескольких резюме с Decisions.

**Можно приглашать ограниченный круг пользователей на alpha-пилот** с описанными
предпосылками установки и обратной связью по ошибкам. Нельзя пока обещать
самодостаточный многорезюмный сервис «скачал и запустил» или стабильный1.x.

Перед таким обещанием нужны самостоятельный поставляемый Decisions-адаптер,
приёмка на чистой внешней Linux-установке с учётной записью другого пользователя
и более широкая проверка смыслового качества. Первый установленный пакет
проверен изолированно, но внешняя подписка другого человека здесь не тестировалась.

Это собственный технический и продуктовый аудит с тестами; независимой экспертизы,
пентеста и юридической сертификации лицензий он не заменяет. Найденные ошибки
устранены, остающиеся ограничения перечислены явно. Версия остаётся **0.1.0 alpha**.
