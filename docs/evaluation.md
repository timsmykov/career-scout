# Контракт оценщиков

Реализован ручной анализатор на LangGraph с native Codex CLI. Владелец12.11
выбрал подписку Codex, gpt-6-luna/max и порядок Product → автоматизация →
бизнес-ассистент → BA. Приёмка смысла вердиктов остаётся отдельной задачей;
unit-тесты и корректные цитаты не заменяют контрольную разметку.

## Ручной запуск

Нужны Python3.12/uv, установленный Codex CLI и `codex login status` с ChatGPT login.
На сервере проверена CLI0.166.0. Model API key не используется; auth.json остаётся
в штатном хранилище Codex и не копируется в приложение или контейнер.
Анализатор работает на хосте, коллектор продолжает работать в своём Docker.

Создайте приватный конфиг по [analysis.example.json](../configs/analysis.example.json).
Пути считаются относительно JSON. `profiles` содержит ровно четыре JSON-снимка
полных резюме с profile_id/resume_id/source_url/title/version/captured_at/text,
content_hash=SHA256 UTF-8 текста и provenance. В snapshot входят авторские разделы
резюме; контакты, навигация, реклама курсов и предложения пройти тест не являются
опытом кандидата. Файлы приватны и исключены из Git.

В рабочем конфиге устанавливаются `order_confirmed` и `external_calls_enabled`;
публичный пример оба флага оставляет false. БД анализатора должна отличаться от
ledger коллектора. Чужая БД с иной схемой отклоняется до изменения.

```sh
# Только подготовка; модель не вызывается. Бюджет0 также допустим.
uv run --no-sync python -m career_scout.analysis prepare --config private/analysis.json --limit 20 --max-calls 80
uv run --no-sync python -m career_scout.analysis run RUN_ID --db data/analysis.sqlite3
uv run --no-sync python -m career_scout.analysis status RUN_ID --db data/analysis.sqlite3
uv run --no-sync python -m career_scout.analysis resume RUN_ID --db data/analysis.sqlite3
# Новое поколение попыток, с явным дополнительным бюджетом
uv run --no-sync python -m career_scout.analysis resume RUN_ID --db data/analysis.sqlite3 --retry-errors --additional-calls 8
uv run --no-sync python -m career_scout.analysis export RUN_ID --db data/analysis.sqlite3 --output data/results.json
```

`prepare` берёт full карточки из согласованного свежего экспорта campaign,
исключает FILTERED_OUT и ещё не обработанные фильтром записи. KEEP обрабатываются
раньше KEEP_UNKNOWN; неизвестные не отбрасываются. Это приоритет обработки,
а не подтверждение соответствия роли. Полное завершение campaign не требуется.
Все четыре входа фиксируются до исполнения; правки резюме и рубрик затем требуют
нового prepare и новых ключей. `run` и `resume` используют уже сохранённые входы.

`resume` сохраняет оставшийся бюджет. `--retry-errors` начинает новое поколение
попыток только для PENDING; валидные ответы берутся из кэша. Завершённые ACCEPTED,
REJECTED и NEEDS_CLARIFICATION не вызываются заново. Экспорт не перезаписывает файл.
Уточнения уже сохраняются в результатах, но интерфейса ввода ответа владельца пока нет.

На одну analysis DB разрешён один исполнитель через flock. LangGraph пишет
checkpoints отдельным соединением с той же БД: разделять соединение с журналом
попыток нельзя из-за фоновой записи. Собственная БД, WAL и результаты приватны.

## Вход

Одна полная согласованная vacancy version, один полный resume version, профиль,
рубрика, явные фильтры, дата оценки, model config/version и схема результата.
Входы фиксируются до вызова; новый текст не подставляется под старый hash.
WorkerInput и EvaluationResult имеют schema_version=2; vacancy — общий v2/common-1.
Дата подготовки — метаданные аудита. Она не передаётся как инструкция судить
по текущей дате и не инвалидирует прежний результат сама по себе.

Не передавать предыдущие оценки, общую биографию из памяти, ключи job-площадок,
инструменты откликов/редактирования. Служебные исходы видит router, не оценщик.
Текст вакансии и резюме — данные, не инструкции менять правила.

Полнота проверяется кодом. При partial/missing/stale текстах до LLM не доходить.
Не сокращать резюме до списка навыков или описания до первых N символов.

## Предметные исходы

PASS: обязанности входят в профиль; основные задачи подтверждены опытом;
существенные обязательные требования имеют достаточное подтверждение; нет
явного конфликта с фильтрами и вопроса, способного изменить решение.
Необязательное требование может оставаться unconfirmed при PASS.

BORDERLINE: роль потенциально подходит, но существенное требование не подтверждено,
неясно обязательное условие или есть конфликт. Назвать конкретный вопрос.
«В резюме нет SQL» не означает «не умеет SQL».

REJECT: обязанности по существу вне профиля или есть подтверждённое несовместимое
обязательное условие. Пример: явно требуется advanced SQL, явно указан только basic.
Не путать отсутствие подтверждения с доказательством отсутствия способности.

Неполный текст, плохая схема, timeout, несуществующая цитата → технический ERROR,
а не один из трёх предметных исходов.

## Короткое обоснование

Только существенные требования/обязанности: короткая цитата вакансии, короткая
цитата резюме при подтверждении, статус confirmed/unconfirmed/conflict и объяснение.
Это проверяемое основание, не chain-of-thought. Не требовать длинную таблицу
для каждого декоративного пункта.

Код проверяет реальные вхождения цитат в соответствующий полный текст/версию.
После canonical whitespace Unicode normalization использовать одну описанную
функцию, не fuzzy matching, который принимает выдуманную цитату.
Реализация — NFC и свёртка Unicode-пробелов, без изменения регистра или пунктуации.
В транспорте source-ranges-1 полные тексты разбиваются без потери символов на
последовательные фрагменты V0001… (вакансия) и R0001… (резюме). Native output
schema принимает vacancy_reference/resume_reference с from/to из коротких ID.
Код восстанавливает непрерывный исходный диапазон длиной до1000символов и
проверяет обычный EvaluationResult v2 с vacancy_quote/resume_quote. Неверный
источник, обратный диапазон или превышение длины дают ERROR. Подстроки не
склеиваются и не исправляются. В журнале попытки сохраняется также wire response.
Это сокращает схему ответа; содержание резюме и вакансии сохраняется полностью.
Изменение представления цитат не инвалидирует ранее проверенные оценки тех же входов.
Цитата должна доказывать утверждение по смыслу; substring check этого не гарантирует,
поэтому качество проверяется ручной разметкой.

kind=responsibility означает основные обязанности, kind=requirement — требование.
Для REJECT достаточно основных обязанностей вне профиля (outside_profile,
mandatory=true/null) либо обязательного conflict с двумя действительными цитатами.
Отсутствие навыка не превращается в conflict. PASS без подтверждений ключевых задач,
REJECT без конкретного основания,
BORDERLINE без конкретного вопроса — schema/semantic validation error.

## Маршрут

Четыре профиля не означают четыре одновременно запущенных процесса. Сейчас
run_pending обходит вакансии последовательно, а LangGraph вызывает один профиль
за раз. Параллельность одного запуска — один вызов Codex. Автоматического
масштабирования и настройки числа параллельных вакансий пока нет.

Конфиг задаёт перестановку ровно четырёх профилей. Подтверждён владельцем порядок:
product → automation → business_assistant → business_analyst.
Публичный пример сохраняет order_confirmed=false; рабочий конфиг фиксирует решение.

Для одной вакансии:
- PASS: сохранить принятие; остальные SKIPPED_AFTER_ACCEPT, не REJECT.
- REJECT/BORDERLINE: следующий профиль.
- ERROR: ограниченные повторы этой попытки; после исчерпания следующий профиль.
- Нет PASS и четыре валидных REJECT: REJECTED.
- Нет PASS, есть ERROR/unrun: PENDING, даже если дополнительно BORDERLINE.
- Нет PASS, все завершены и есть BORDERLINE: NEEDS_CLARIFICATION.

Поздний PASS достаточен даже после раннего ERROR. Выбран первый подходящий профиль,
не обязательно лучший из четырёх. Sol не включён в обязательный граф.

## Версии и стоимость

evaluation_key = hash(source + source_id + vacancy_content_hash + resume_hash +
profile_id + rubric_version + filter_version + model_config_hash + evaluator_version).
route_key дополнительно содержит policy/order version и версии всех четырёх профилей.
Изменение порядка может переиспользовать валидные индивидуальные оценки, но требует
новой агрегации. Ошибка не кешируется как REJECT.

Число попыток, входные/выходные токены (если провайдер возвращает), latency и стоимость
сохраняются отдельно. Неизвестная цена → cost_unknown, не 0.
Для подписки денежная стоимость неизвестна: cost_usd=null, не0. Конечный max_calls
сохраняется до начала попытки; после сбоя он может консервативно учитывать попытку
без полученного ответа. max_attempts_per_profile ограничивает повторы в поколении.
Таймаут и Ctrl+C останавливают только процессную группу своего воркера. Превышение локального
max_input_characters даёт ERROR, текст не обрезается. Auth/model/schema/rate-limit
ошибка останавливает batch с PENDING; другая модель или аккаунт не подставляются.
Worker работает без инструментов, памяти и прошлых оценок, в отдельной ephemeral
сессии Codex. Успешные ответы фиксируются до checkpoint; сбой после этого не требует
нового модельного вызова. Настоящее выполнение и качество оцениваются отдельно.

## Первые содержательные проверки

[Результаты первого прогона и найденное замечание](quality-first-20261112.md).

Контрольные вакансии: [evaluation-quality.json](../tests/fixtures/evaluation-quality.json).
Это восемь явно вымышленных примеров с настоящими приватными ролевыми резюме:
четыре подходящих роли, желательный навык, неизвестный обязательный навык,
явный конфликт уровня SQL и нерелевантная роль с подменой инструкций.
Зарплата в этих примерах не задана и не должна мешать принятию.

```sh
# Зафиксировать входы и ожидаемые статусы без вызова модели
uv run --no-sync python scripts/check_evaluation_quality.py --config private/analysis.json --output data/quality-first --max-calls 8
# Запустить ровно по одной попытке на пример; продолжение использует сохранённое
uv run --no-sync python scripts/check_evaluation_quality.py --output data/quality-first --resume --execute
```

Исполнитель использует тот же CodexWorker, EvaluationResult и проверку цитат, что
основной анализатор. Manifest и hash ожидаемых статусов сохраняются до inference;
эталон и его объяснение не передаются оценщику. Ответы, usage и технические ошибки
хранятся в отдельной приватной SQLite, сводка — results.json. Несовпадение даёт
label_match=false, а не повтор до нужного ответа. Возобновление не повторяет
ошибочную попытку автоматически и не увеличивает бюджет.

Это проверка очевидных правил, а не репрезентативная оценка точности на рынке.
Обоснования и связь цитат с выводом проверяются вручную. Примеры, рубрики и их
проверку готовит один автор; независимой экспертной разметкой это не является.
Следующий уровень — отдельно размеченные реальные вакансии, включая спорные
случаи, и проверка устойчивости на повторениях без изменения эталона после ответа.
