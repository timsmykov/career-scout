# Конфигурация поиска и фильтры

Реализованы для HH без LLM. Рабочий файл — [configs/search.toml](../configs/search.toml),
валидируемый через Pydantic; `--config PATH` выбирает другой файл. Старые
`project.example.toml`/`search.example.toml` остаются проектными черновиками,
runtime их не читает. Зарплата не участвует в отборе: отсутствие суммы нормально,
минимума/максимума дохода и требования публиковать зарплату нет.

## Поисковый план

`plan` показывает запросы, UTC-окно, географию, бюджеты, политику и её hash без
credentials, HTTP или открытия БД. `collect` фиксирует этот план в run.

По умолчанию четыре семейства: product, business_analyst, business_assistant,
automation. Сначала идут четыре запроса с технологическими уточнениями
IT/финтех/ИИ/ML, затем 12 более широких запросов, по очереди из каждого семейства.
Одинаковые запросы объединяются с сохранением всех семейств происхождения.
Обязательного слова «ИИ» нет. Это расширяет охват по сравнению с одними
технологическими запросами, но не доказывает полноту или релевантность выдачи.
При малом бюджете обработается только часть плана; остаток сохраняется для resume.

Явный `--query` заменяет все семейства точными переданными запросами. Можно повторять.
География `area_ids=[]` не ограничена; конкретные HH IDs можно добавить в TOML.
Поиск не отправляет API-фильтры experience/industry/salary/only_with_salary:
иначе карточки с неизвестными полями могли бы исчезнуть ещё до чтения.
Всегда отправляется `no_magic=true`, чтобы HH не превращал текст запроса в
неявные ограничения. Поведение параметра описано в [HH OpenAPI](https://api.hh.ru/openapi/redoc).
Значения API проверяются на mock-транспорте; это не обещание охвата всех вакансий.

## Отбор после полного описания

| Критерий | Как проверяется |
|---|---|
| Сфера IT, финтех, ИИ/ML | Лексические признаки в названии, полном тексте, названии компании или структурированной отрасли; технологическая функция **или** работодатель |
| Стажёр, junior, middle | Явные обозначения собственного грейда в названии; из числа лет грейд не выводится |
| Без опыта или 1–3 года | Нормализованная API-категория плюс ограниченный разбор явно обязательного собственного стажа в полном тексте |
| Зарплата | Не читается алгоритмом принятия решения |

Каждый критерий получает `allowed`, `excluded`, `unknown` или `conflict`, код причины
и поле/цитату основания. Нетехнологическая сфера доказывается только сочетанием
явно посторонней роли в начале названия (например, курьер) и всех указанных отраслей
из короткого списка посторонних отраслей. Отсутствие IT-слов само по себе не отказ.
Технологические сигналы имеют приоритет над этим исключением. Словари настраиваются
в TOML; это консервативный лексический фильтр, а не смысловая оценка соответствия резюме.

Явные senior/lead/head исключаются, если это грейд самой вакансии. Упоминание
senior-коллеги в описании, «ассистент руководителя» и lead generation не считаются
высоким грейдом. Смешанные junior/senior и распознанные отрицания сохраняются как conflict.
Неоднозначные названия, которые правило не распознаёт, остаются unknown.

API-категории 3–6 и более 6 лет исключаются при отсутствии противоречащего условия.
Явный обязательный минимум выше 3 лет тоже исключается. Ровно 3 года допустимы;
диапазон оценивается по нижней обязательной границе. Желательный опыт, стаж коллеги
и возраст компании не используются для отказа. Распознавание текстовых требований
ограничено явными конструкциями вроде «Опыт работы от 5 лет» и «5+ years of experience»;
непонятная формулировка не получает выдуманного значения. Противоречие между API и
распознанным текстом сохраняется как conflict.

| Итог | Значение |
|---|---|
| `KEEP` | Все три критерия явно допустимы |
| `KEEP_UNKNOWN` | Нет доказанного исключения, хотя бы один критерий неизвестен или противоречив |
| `FILTERED_OUT` | Хотя бы один критерий содержит доказанное исключение |

Неизвестный критерий никогда сам не исключает вакансию. Но неизвестная сфера
не отменяет отдельное явное ограничение, например senior. `KEEP` не означает
соответствие кандидату: резюме и агенты на этом этапе не используются.
В конфигурации `keep_unknown` и `salary_optional` допускают только `true`.

## История и повторная фильтрация

Все full карточки остаются в SQLite, включая исключённые. Решения хранятся отдельно
с ключом source+source_id+content_hash+normalizer_version+policy_hash. Hash политики
включает её значения и версию движка `rules-2`; повторный запуск идемпотентен.
`inspect` показывает основания и историю. Изменённое содержимое требует нового решения:
старое положительное решение не пропускает новую версию автоматически.

`resume` использует сохранённые запросы, географию и активную политику run, а не
текущий TOML. Бюджеты берутся из сохранённого плана, CLI может переопределить их
для одного вызова. Редактирование TOML влияет на новые collect. Для явного
пересмотра старого run без сети:

```sh
docker compose run --rm collector refilter RUN_ID
docker compose run --rm collector status RUN_ID
docker compose run --rm collector export RUN_ID --output /data/exports/selected.json
docker compose run --rm collector export RUN_ID --include-excluded --output /data/exports/all.json
```

`refilter` активирует текущую политику и пересматривает все полные текущие карточки
run, сохраняя прежние решения и первоначальный план. Обычный export выбирает
`KEEP`+`KEEP_UNKNOWN`; `--include-excluded` выгружает все full карточки. Обе формы
содержат `selection` и отдельные `filter_decisions`. Если текущая версия ещё не
проверена, она видна как `pending` и не выдаётся за отобранную. Старый run без
активированной политики экспортируется без отбора с `applied=false`.
Статус сбора complete/partial и количество full карточек не подменяются количеством
прошедших фильтр. Экспортный формат вакансии остаётся v2, схема SQLite — v3.
