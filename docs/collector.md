# Сборщик

## Решение

Свой небольшой API-агрегатор поверх httpx, отдельный адаптер каждой площадки.
Основной референс ru-it-jobs-radar — механизмы, а не готовая база целиком.
HTTPX — транспорт; LangGraph не нужен для обхода страниц.

## Интерфейс адаптера (целевой, пока не код)

- capabilities() → официальный/неофициальный транспорт, поля, пагинация, пределы.
- plan_queries(profile_families, attributes) → адресные SourceQuery.
- fetch_page(query, cursor, budget) → items, next_cursor, totals, warnings.
- fetch_detail(source_id, listing_snapshot, budget) → snapshot + detail_status.
- normalize(payload) → общий VacancySnapshot без догадок о пропущенных полях.

Cursor типизируется по источнику: HH page с нуля, Habr page с единицы,
Trudvsem offset как номер страницы, SuperJob page с нуля + окно дат.
Нельзя обобщить всё как offset += page_size.

## План поиска

Каждое семейство профиля имеет несколько фраз по названиям и обязанностям.
Выполняется объединение, не пересечение. Слово AI/ИИ не обязательное.
Список рабочих фраз — configs/search.toml; example остаётся шаблоном.
Запросы не строятся автоматически LLM в каждом прогоне.

Не делать title-only основным ограничением. Технологический домен и уровень
уточнять по карточке. Серверный фильтр опыта можно включить только при проверенной
семантике: исключающий unknown фильтр требует дополнительной широкой ветки.
До измерения потерь default — широкие запросы и локальная проверка.

Запросы чередуются по семействам; площадки обрабатываются порциями HTTP.
Порции не ограничивают общий объём площадки: HH может дать существенно больше ID. Snapshot query plan фиксируется в run.
Свежесть сортирует очередь, но не превращает хвост в отказ.

## Страницы и окна

Каждая успешно записанная страница сохраняет cursor/окно, IDs и counters.
Новый cursor фиксируется после записи всех полученных строк и ошибок строк.
Сбой в середине допускает повтор страницы: exact dedup защищает реестр.

Если источник ограничивает доступную глубину:
1. Применить поддерживаемые источником временные окна с перекрытием границ.
2. Дедуплицировать по source+source_id.
3. Если минимальное окно всё ещё переполнено, зафиксировать truncated.
4. Не обещать полноту по found и не считать недоступный остаток нерелевантным.

Окна/словарные разделения должны покрывать исходный план. Нельзя обходить лимит
без проверки разрешённых параметров или скрыто сужать смысл запроса.

## Общий HTTP

Timeout конечный; явный User-Agent/contact. TLS verification включена.
Разрешённые хосты адаптера задаются явно; произвольные внешние URL из текста
не загружаются. Переход на auth/captcha/другой host — состояние, не описание.

401 → auth_required. 403 → access_denied/captcha_requires_action по контракту.
Остановить соответствующий источник; не подменять его браузерным обходом.
429 → cooldown источника, Retry-After секундный или HTTP-date; finite retry.
5xx/transport → ограниченный backoff с jitter. SuperJob 503 может означать квоту:
консервативный cooldown, не считать обычным бесконечным server error.
Не повторять permanent schema/400 ошибку неизменённым запросом.
Новые необязательные поля допустимы; сломанные обязательные поля — rejects log.

Общий бюджет включает search, detail и повторные попытки; token refresh учитывается
отдельно. Перед запросом резервировать слот/бюджет, а не после исполнения.
min_interval_seconds — наша настройка, не опубликованная квота провайдера.

## Detail

Основной initial/new сохраняет listing неизвестного ID и дочитывает его описание.
Уже сохранённые карточки не обновляются по TTL или изменению listing. Старый
недочитанный хвост переносится в новый проход. Trudvsem full объекты из списка
сохраняются через тот же normalizer без повторного GET. Изменения ранее сохранённых
карточек и проверка закрытия вакансий исключены владельцем из текущего этапа.
Legacy collect продолжает поддерживать прежнее TTL/stale поведение.

404/410 карточки → unavailable/archived по фактам, не REJECT кандидата.
Пустой/короткий текст не полнота. HTML очищается с сохранением разделов/списков.
Запретить silent truncation при передаче в LLM: превышение контекста — отдельная ошибка.

## Актуальность первичного сбора

Initial ограничен14днями по дате публикации. Границы фиксируются при старте и
передаются HH/SJ; Trudvsem дополнительно проверяется по creation-date, Habr по
publishedDate/JobPosting.datePosted. Обновление не делает старую публикацию новой.
Вне диапазона не запрашивается отдельный detail; неизвестная дата хранится и
показывается отдельно, без включения в свежий экспорт. Старый архив не удаляется.

## Полнота и watermark

Run хранит planned/completed queries, pages, total_reported, distinct IDs,
detail_full/deferred/failed, capped_windows, rejected_payloads, request counts.
collection=complete относится только к выполненному плану, не ко всему рынку.
detail_complete — отдельно.

Watermark продвигается только по полностью пройденному конкретному source/query/window;
не единый global timestamp после частичного сбора. При incremental использовать
перекрывающий lookback, exact dedup и периодическую сверку. Watermark берётся
из гарантированной семантики источника, не произвольного max(fetched_at).
В initial/new исключающий watermark не используется: каждый ручной new снова
обходит все доступные списки и дедуплицирует ID. Первое известное ID не является
условием остановки. Это позволяет подхватывать поздние и поднятые объявления.
Описания известных ID повторно не скачиваются.

## Дедупликация

Одна карточка в разных запросах: одна identity, несколько discovery records.
Другой source ID — отдельная запись. Похожая компания/название может предлагать
разные роли; semantic dedup не удаляет записи автоматически.
content_hash строится по значимым полям и тексту; raised/view counters исключены
только после проверки полей конкретного источника. Различать raw_hash и content_hash.

## Ошибка источника

Остальные доступные источники могут завершить работу. Итог явно partial/blocked,
а не «новых вакансий нет». Остаток сохраняется с причиной и курсором.
